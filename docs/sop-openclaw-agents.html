What this page is: how to work with, train and develop any of our OpenClaw AI agents. It is generic — nothing on this page is specific to one agent. For the agent you actually work with, read this page first, then its own page. Anything marked ADMIN is not yours to change — ask.

1. What OpenClaw is

OpenClaw is the gateway that lets our AI agents live in chat. It runs on our own Raspberry Pi — not in the cloud — and does three things: it holds each agent’s identity and memory, it connects agents to Slack, Telegram and (soon) WhatsApp, and it gives each agent a set of tools it is allowed to use.

An agent is not a chatbot with a clever prompt. Each one is:

A project folder

Real code — the tools the agent can call, plus the database and scripts behind them

A workspace

Its behaviour files, skills and memory — what it knows and how it decides

Channel bindings

Which Slack channel or Telegram topic it listens in, and who is allowed to talk to it

Several agents run on the machine, each isolated from the others. You will normally be given access to exactly one. This page tells you how to work with it; its own page tells you what it is for.

Rule of thumb: if the agent tried and failed because a tool doesn’t exist or is broken → Claude Code. If the agent had the tool but reached the wrong conclusion → chat.

Never edit ~/.openclaw/openclaw.json. One file defines every agent on the machine, and each agent’s tool server is wired to it by absolute path. A bad edit takes down all of them at once, not just the one you were working on. If something needs changing there, raise it with the admin.

Being in the channel is not the same as having access. Telegram in particular has a second gate: being added to a group or topic lets you see the conversation, but a separate allowlist in the gateway config decides whether your messages are processed. Until an admin adds your user ID, the agent simply will not respond — and your messages and commands are dropped silently, with no error. If a channel feels dead, that is almost always why. Ask the admin; they can read your user ID off the group member list.

5. Context and sessions

A “session” is one continuous conversation with its own memory. Where you type decides which session you land in — and therefore who you are sharing a brain with.

Where you type

Session behaviour

A Telegram topic

One session shared by everyone in the topic

A Slack channel, top level

One session shared by the whole channel

A Slack thread

Its own separate session, seeded with the last ~20 messages of that thread

Every day at 04:00

Sessions reset automatically — a morning question starts clean

A shared channel is one shared brain. Everyone posting in the same channel or topic is in the same conversation with the same memory. If two people work different problems at once, they will confuse each other and the agent. Coordinate, or take the second piece of work into a Slack thread.

Practical habits:

  • One task per session. Two unrelated jobs in one conversation makes the agent worse at both.

  • Use Slack threads to work in parallel. A thread is effectively a private workspace.

  • When it starts forgetting, don’t repeat yourself — /compact. The agent summarises itself and carries on.

  • Don’t rely on chat as memory. Anything that must survive belongs in a skill or a knowledge file. Ask the agent to write it down.

  • Compaction also happens automatically and silently near the context limit. Nothing is lost from disk — only from what the agent is holding in mind.

6. Training an agent

Training happens in chat, and Telegram is the better surface for it. The goal is never to win one argument with the agent — it is to leave behind a written rule that survives the next reset.

  1. Show it the case. Point at something specific — a reference number, an ID, a date — not a vague description.

  2. Ask for its reasoning before you correct it: “why did you conclude that?” Often the data is wrong, not the logic, and the fix is somewhere else entirely.

  3. Give the rule, not just the answer. “This one is wrong” teaches nothing. “Whenever X happens, do Y, because Z” teaches a rule.

  4. Ask it to write the rule down — into a skill or a knowledge file, as a proposal.

  5. Test it. Ask the agent to apply the new rule to two or three other cases and show its working.

  6. Hand to admin for approval.

There are three layers you can propose changes to, in rising order of risk:

LOWEST RISK

Skills & knowledge — how it handles a particular supplier, customer or case type

MEDIUM

Answers to its decision queue — supplying facts it asked for. Safe work, and genuinely useful.

HIGHEST

Core behaviour files (AGENTS.md, IDENTITY.md, EXPERTISE.md) — red lines, reporting style, domain maps. Propose, never apply.

7. Propose, don’t apply

Assume the agent will do what you ask. If an agent has write access to a real system, nothing in the software stops a VA from triggering a real change. The boundary below is a rule you follow, not a lock on the door.

  1. Ask for a dry run first. Write tools default to dry_run=true. Say “show me the dry run” and read the output before anything else happens.

  2. Say the words. Open the task with “propose only, do not apply”. Our agents are instructed to treat that as binding for the rest of the session: they will refuse applying tools and tell you what they would have done.

  3. Let it write proposals to file — the pattern is a section headed # Proposed update: inside the relevant file. Admin reviews and merges.

  4. Never ask an agent to apply proposals, approve anything, or flip a rule live. That is the admin’s call.

Approval prompts you may not be able to clear. Some changes — particularly to an agent’s own configuration and rules — raise an approval prompt that must be tapped in the owner’s main Telegram chat. VAs do not have that chat, and may not have approval rights at all. If an agent goes quiet and seems to be waiting for something, this is the most likely reason — ping the admin rather than retrying. Exactly which actions trigger it for a VA account is worked out per person during onboarding.

8. Developing with Claude Code

Point Claude Code at the agent’s project root — the folder holding its code. Not at workspace/ on its own, and not at your home directory.

cd /path/to/the/agent/project
claude

Each agent repo carries its own CLAUDE.md with the rules for that project. Claude Code picks it up automatically — you don’t need to paste instructions.

Green — go ahead

  • src/ — the tools and logic

  • migrations/ — database schema changes

  • scripts/, knowledge/, workspace/skills/, planning docs

Red — stop and ask

  • .env and .keys/ — live credentials, and owner-only on disk anyway

  • ~/.openclaw/openclaw.json — gateway config, outside every repo

  • Anything that performs a real write against a live external system outside dry_run

  • Anything under /var/www/ or a production database

You will not be able to run everything. Reading, editing, git and type-checking work under your own login. But most of these projects validate their credentials at startup, so anything that actually executes — the tool server, sync scripts, most tests — will fail without .env, which you don’t have. Write and type-check your change, then ask the admin to run it.

9. Escalate to admin when

  • A real write needs to actually happen in a live system
  • The agent appears to be waiting on an approval you can’t give
  • A sync or job fails twice in a row, or reports credential / permission errors
  • You believe a red line in AGENTS.md is wrong or out of date
  • Anything involving .env, credentials, or openclaw.json
  • The agent stops responding on a channel entirely
  • You need access to a channel, a Pi login, or a new agent
